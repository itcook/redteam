## 四条开工裁定（2026-10-02 用户裁）

| # | 裁定 | 被否的选项与理由 |
|---|---|---|
| 1 | **只做激活、挂全量轮**；`--incremental-from` 继续 bail | 连带重建 M13 增量轮要先重裁「上轮 finding 要不要携带」（`carry()`/`merge_carry()` 全是 Finding 形态，而新形态下 finding 只由深挖产出），范围大几倍且牵出未裁的设计问题。激活所需输入在全量轮上已全部具备。 |
| 2 | 排序**新增独立层「激活」，插在「代码优先」之后、「烟量」之前** | 插在风险档之后 → 被激活的文档疑点会排到未激活的代码疑点前，与 C0 刚钉死的代码优先冲突；`risk_band +1` → risk_band 是区域属性、由风险评分器算，写入疑点级激活会污染语义且下轮重算即丢。 |
| 3 | 收敛口径**严格：`file ∈ delta ∧ status == dormant` 即未处理** | 「入队即处理」会把「入队了却又被预算截一次」记成已处理，债静默消失。有截断就不收敛是特性不是缺陷——收敛是给 ship 循环的停止条件、不进 verdict，下轮预算重置 + delta 缩小后能消化；死锁风险由活锁守卫兜底，故守卫是本口径的**配套而非可选项**。 |
| 4 | 活锁守卫**两段式：N=3 强制入必挖集，N=5 停车交人** | 直接停车放弃了「强制必挖可能一次挖出来」的自愈机会；只必挖不停车则真挖不动的疑点每轮占一个必挖位，成长期税。 |

## Requirements

### C-1 增量激活（roadmap 项 2）

- **时点**：scan 完成、入队前。现落账/披露都在深挖**之后**（`cli/mod.rs:457-460`），激活必须在之前。
- **判据**：`file ∈ changed_files` ∧ `status == dormant` ∧ `last_job != 本轮 head`。
  第三项同时排掉两种假激活：本轮自产的（本轮刚截断，激活了也无预算）、同 HEAD 重跑的（无新 delta）。
- **闸门**：上轮 verdict == Incomplete → 整轮不激活（design §8.3 preflight 守卫扩展）。
  上轮 = `results` 表按 `created_at` 最近一条（本轮尚未写入，故最近一条即上轮）。
- **重锚**：复用 `positioning::anchor_near`（quote 从台账行 json 取）；重锚失败 → 不激活并计数。
- **入队**：构造 `EnqueueReq` 走既有入队流程；与本轮 scan 疑点撞 id 时按既有合并语义合并（同一处疑点本轮又被扫到，合并是对的）。
  合并时 `activated` / `force_dig` **取并**——入队序是 H0 → scan 格 → 激活项，激活项通常是后到的那个，
  所以「并进已有项」是常态；不取并等于把提档与强制必挖静默丢掉（dogfood 抓到）。
- **晋升**：本轮挖出 finding 的激活项 → 对应台账行写 `promoted`，退出激活池。少了它，已经报出来的疑点
  会被后续每轮反复重挖、计数涨到停车门，然后报告说「机制挖不动它」，而它明明挖出来了。
- **`--no-dismissed` 必须关掉每一条台账路径**（激活 / 晋升 / 落账 / 披露 / 收敛）：
  该旗的语义是「本次评审完全关闭台账」，而新加的路径各自解析项目库路径、都没问过它（dogfood 抓到，
  这是本仓第六次栽在「同一件事不在两处各有一套」）。用遍历式不变式测试兜底，不逐条断言。
- **落账回写**：激活成功 → `activations += 1`、`last_job` 记本轮，**不动 `status`**。

  > 实施中改过一次口径（2026-10-02 dogfood 抓到）。原案是 `dormant → activated` 的三态单向机，
  > 与本 PRD 自己的三处定义冲突：① 裁定 3 把「未处理」定为 `status == dormant`，而激活一改状态，
  > 一个「激活了又被预算截断」的项就离开了维度 2 的集合——正是裁定 3 明确否掉的「激活即处理」；
  > ② 判据（上一行）要求 `status == dormant`，状态一改就再也激活不了，`activations` 饱和在 1，
  > 而两段门在 3 / 5 → **活锁守卫是不可达的死代码**；③ 这类行从此既不激活也不披露，彻底消失。
  > 改为两态（`dormant` / `promoted`）：同轮幂等由 `last_job <> 本轮` 保证，跨轮每轮各加一次，
  > 门才可达；挖出 finding 时才写 `promoted`（新增 `promote_dug_suspicions`，见下）。

### C-2 收敛三维 + 活锁守卫（roadmap 项 3）

- RunMeta 新增 `converged: bool` 与三个分量，**不进 verdict、不改 exit_code 五档**（10/2/0/3/0）。
  - 分量 1 无 blocking findings（复用 `verdict::blocking_count` 同一谓词）
  - 分量 2 台账无 delta 邻接 dormant 项（**落账之后**算，与收敛口径裁定一致）
  - 分量 3 无激活超限项（`activations >= 5`）
- 活锁守卫：`activations >= 3` → 本轮强制 `must_dig`（不受预算截断）；`>= 5` → 停车，报告给可读理由 + warning。

### C-3 ship 协议消费新字段

- `plugins/redteam/commands/ship.md` 读收敛三维决定是否继续循环；`make gen` 同步 codex-skills，`make verify` 绿。

### 顺带修（摸底撞见，落在本批范围内）

- **披露段口径**：`report.rs:150` 与 md 输出都写「台账里的**历史**截断项」，实现是落账之后读
  （`cli/mod.rs:462` 注释自承「本轮刚截断的也会出现」）。实测 164 条里 159 条是本轮自产。
  批 C 必须区分两者（激活只能对真历史生效），故一并把披露面的口径与文案对齐。
  注意这批项已被 `deep.budget_skipped` 披露过一次，避免同一事实两处不同口径。
- **`ledger.rs` 错误前提**：注释称「needs 补查项 `members` 恒空 → 不会落账」，但 PR181 库里有一条
  `origin='Needs'` 的落账——needs 项与 scan 疑点合并进同一队列项时（`queue.rs:492` 吸收 `req.spec.notes`），
  scan 疑点就跟着 needs 项的身份落了账。缺口本身（纯 needs 项无独立身份、批 C 捞不回）为真，
  但该解释不成立；注释原话即「别让批 C 按错误前提实现」，故本批订正。

## Acceptance Criteria

- [x] **激活正路**：构造 delta 命中台账的用例 → 休眠疑点被激活、进队列、`status/activations` 已回写。
- [x] **三类不激活**：① 本轮自产（`last_job == 本轮 head`）② 同 HEAD 重跑 ③ 上轮 Incomplete — 各一条用例。
