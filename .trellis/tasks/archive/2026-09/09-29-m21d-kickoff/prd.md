## 开工必须先纠正的两件事

### 一、L4-B 的验收对象写错了：PR181 里**一行 Rust 都没有**

roadmap 验收写「三方契约：**PR181** 每 PR callee 注入数与 input 增量可观测」，而交付项 1 是「Rust 先行」、
「非 Rust 生态定位链」明确列在**不做**里。实测 PR181 的语言构成：**15 个 `.ts` + 10 个 `.go` + 9 个 `.md`，零 Rust**。
→ 交付项 1 / 2 在 PR181 上**不可能产生任何注入**，这条验收自相矛盾。

**校正**：L4-B 的验收对象改为**本仓自评审**（redteam 是 Rust 单 crate、16 个直接依赖，
`~/.cargo/registry/src/index.crates.io-*/` 在本机齐备，正是 L4-B 的用武之地）。
PR181 继续作为 Go/TS 侧的回归靶子，但不背 L4-B 的指标。

### 二、撤回「L4-B 是 PR181 覆盖缺口的药」——我此前的判断不成立

M21c 开工时我写过「尸检指向覆盖缺口的药是 M21d 的三方契约注入（T7 = 两个函数的契约分叉）」。**核对后不成立**：

| 漏检主题 | 实际形态 | L4-B 能否覆盖 |
|---|---|---|
| T7 error-code fork | `mapSafeErrorCode` 与 `mapErrorToCode` 分叉——**同一仓内两个函数**，且在 `.ts` 文件 | 否（既非三方 callee，也非 Rust） |
| T6 body 未 cancel | 单文件内的资源生命周期 | 否 |
| T8 two-delivery ceiling | 跨文件不变式 | 否 |
| T11 吞吐假定不可调 | 单点常量 | 否 |
| T12 日志不分瞬时/终态 | 同 T7 区域 | 否 |

**一条都不是「三方库 callee 契约误用」**。L4-B 注入的是三方库的签名 + doc，对「仓内两个函数不一致」帮助有限。

→ **M21d 补的是上下文盲区，不背 PR181 那批覆盖缺口的指标**。那批缺口（模型看着正确的代码、写出别的缺陷）
更可能要靠「reviewer 的类别清单 / 注意力」或「同项多采样取并集」来治——**需要单独立项**，不在 M21d 范围内。
这是我第三次修正自己的判断（前两次：判例前移不是覆盖的药、拆大组不省墙钟），记在这里免得后人照着错误前提排期。

## 批次划分

## 约束（继承仓内惯例）

每处行为改动配会转红的用例 + 变异检查（**脚本本身也要被怀疑**：批 0 有 2 条假绿是脚本判据与范围写错造成的）；
私有数据只落 `.next/private/`；`make verify` 绿；改代码走小分支、合回前过 `/code-review`。
**警惕「各自绿、接起来不通」**：M21c 批 A 连续两次栽在这上面（接管挂错层、resume 第二条出口漏挂），
新增跨层接线一律配一条**集成级**用例。
