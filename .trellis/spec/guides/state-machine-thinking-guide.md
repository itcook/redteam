# 状态机思考指南

> **用途**：动到「有状态的东西」之前，先回答两个问题——**谁写每个状态？从每个状态出得去吗？**

本仓已经在这上面栽过两次，两次都是**单测绿着而功能是死的**。下面的检查项都是实证来的，不是通则。

---

## 什么算「状态机」

不限于 `enum`。只要满足这两条就算：

- 一个值有**有限几种取值**，且
- 某些取值之间有**转换**（不是一次性赋值后就不变）

本仓的例子：`JobStatus`、`Phase`、`ItemState`、`suspicions.status`、`dismissed.status`。
队列项、台账行、作业记录——凡是「跨轮 / 跨进程存下来、后面还要改」的，都在此列。

---

## 开工前：列「状态 × 谁写它」表

对每个状态，填这三列：

| 状态 | 谁写它（产品路径，排除测试） | 从它出得去吗 |
|---|---|---|
| … | `fn xxx` / 某子命令 / 某协议步骤 | → 哪些状态；没有出口则说明为什么是终态 |

**怎么填「谁写它」**：grep 这个状态的字面量，然后**逐个判断是产品代码还是 `#[cfg(test)]`**。
这一步不能省——本仓 `Phase::Refute` 看起来有两处写入，查下来两处都在测试模块里。

### 三种一眼可见的病

**① 某状态没有产品 writer。**
定义了、文档说它存在、实际没人写。

> 这一条可以**推广到任何「定义了却没人用」的东西**，不限于状态：观测字段、warning 文案、
> 配置键、报告字段都一样。判据同一句话——**grep 它的消费方，排除测试，看还剩几个**。
>
> **反向同样要查：有消费者的字段，谁在写它？** 本仓的 `Finding.previously_dismissed` 有消费者
> （`blocking_count` 的「人已驳回 → 不 blocking」）、有测试，而 writer 随一次删除没了之后
> 没人补——这类缺口比「没人读」更隐蔽，因为消费侧的代码和测试都好端端地在那里绿着。
> 实例：M21c 批 B 给跨文件重定位加了 `AnchoredScan.relocated` 计数，字段、累加、单测都齐，
> 但**没有任何地方把它读出来**，于是那一层在真实运行里完全不可见。加观测的同时要接出口。
> 实例：`Phase::Verify` 在 M21b 批 C 占位、批 D 做了复核却没接打点，全仓零产品写入，
> 于是后台作业跑在复核尾段时 `status` 显示的还是 `deep`。
> 反例要分清：`Phase::Fanout` / `Refute` 也零写入，但注释写明是**历史兼容**（旧作业 state 仍可读），
> 那是故意的。判据是「注释有没有说清楚为什么没人写」。

**② 某状态出不去（缺回边）。**
进得去、出不来，而业务上它应该能回来。
> 实例：台账的 `dormant → activated` 是单向的，而「激活了但没挖成」恰恰是最常见的情形
> （本轮预算同样会截断它）。后果：`activations` 永远饱和在 1，而活锁门在 3 / 5——
> **两段守卫整个是不可达的死代码**；更糟的是这类行从此既不被激活也不被披露，彻底消失。
> 问法：**这个状态的「失败路径」会把它带到哪去？** 不是只想成功路径。

**③ 终态没说清楚自己是终态。**
`Settled` 不需要回边，但得有地方写明「这是终态」。能自我声明最好。
> 正面样板：`JobStatus::is_terminal()` 把终态集合写成代码，而不是散在注释里。

**④ 分支可达，但**喂给它的那类输入**到不了这个函数。**
判定函数本身被调用着、分支里的 return 有消费方、单测直接构造输入把它测得好好的——
grep 一路绿，可真实输入分布里永远不出现那一类。**① 的 grep 判据对这种病完全无效。**
> 实例：`VerifyDecision::SkipCarried` 由 `decide` 产出、`reason()` 把它分类、`--help` 列着
> `carried` 这个跳过分类、单测直接搓 `origin: Carried` 的 finding 测它——全绿。
> 而 `decide` 的唯一产品调用点在 `deep.rs` 的 landed 循环里，只遍历**本轮格的输出**，
> 那些 finding 的 `origin` 恒 `New`（`Origin::Carried` 的唯一产品写入点在 `carry::carry`）；
> carried finding 走的是收场的 `findings.extend(prior_findings)`，根本不经过 `decide`。
> 于是这个分支**自引入起就不可达**，carried 一律沿用往轮判决、从不重验，
> 连「往轮压根没判过」的也照沿用。
>
> 问法不是「谁引用了它」，而是**「什么样的输入会走到这个分支？那种输入真的会到达这个函数吗？」**
> 查法：找这个分支的判据字段（这里是 `Finding.origin`），grep 它的**产品写入点**，
> 再看那些写入点的产物**流向哪条路**——和本函数的调用点是不是同一条。
>
> 这类病在重构里高发：M13 的复核在 reduce 层（对合并集跑，carried 自然在内），
> M21 改成 deep 层逐格流式之后，carried 就没有挂点了，而判定函数原样搬了过来。
> **搬判定逻辑时要连它的输入来源一起搬**，否则判据还在、输入没了。

**找到之后怎么处置：三条路，按「真跑到了会怎样」选。**

1. **接上输入**——该分支本来就该走到。`SkipCarried` 属这类：补上 carried 的复核挂点，
   分支立刻可达，用例也写得出来。
2. **删掉**——语义已经不成立、真跑到也无意义。
3. **铉住不变量**——确实不可达，但一旦跑到后果很重。
   别留一个静默 `return` 假装处理过：**debug 下 `debug_assert!(false, "<为什么不可达>")`、
   release 下披露**，然后把真正的保护写成**上游的不变量用例**。
   > 实例：`enqueue_activated` 里 `from_ledger` 返回 `None` 的分支。账上记作「静默丢弃」债，
   > 核下来是不可达（`line_start.max(1)` + `line_end.max(start)` 对上
   > `QueueItemSpec::new` 只拒 `a == 0 || b < a`）。没删，因为后果重：台账回写
   > （`activations` +1）在 CLI 层**早于**入队，真丢会让疑点假性逼近活锁门，
   > 最后报告对人说「机制挖不动它」而它一次没被挖过。
   > 守住它的是 `from_ledger_never_fails_on_any_ledger_row`（拿 `(0,0)` `(5,0)` `(u32::MAX,0)`
   > 这类边界值逐个压），**不是那段分支代码**——分支自己永远测不了。

第 3 条是关键区别：不可达的分支**不能靠它自己的用例保护**。要么把保证它不可达的
那条不变量写成用例，要么就是在裸奔。

## 写代码时：保护放在入口，不放在调用点

**正面样板 —— `JobStatus`**：所有状态写入都过 `JobStore::update_if_active` 这**一个**口，
终态封盘（`if st.status.is_terminal() { return None }`）就写在那个口里。
保护是**结构性**的，不靠每个调用点自觉。新加一条写入路径也自动受保护。

**反面 —— 批 C 的台账**：激活 / 晋升 / 落账 / 披露 / 收敛五条路径各自解析项目库路径，
于是 `--no-dismissed`（「本次评审完全关闭台账」）被**五条路径集体绕过**——
一轮「要求忽略台账」的评审反而被台账操纵了。这是本仓第六次栽在「同一件事不在两处各有一套」。

> 加第 N 条读写同一份状态的路径时，先问：**第 N+1 条加进来时，谁会提醒他过这道门？**
> 答案如果是「靠记得」，就该把门收进唯一入口，或者加一条**遍历式**不变式测试（见下）。

## 写测试时：夹具不能绕开被测路径

**这是本仓最贵的一课。** 批 C 的活锁守卫（3 次强制必挖 / 5 次停车）在真实路径上整个是死代码，
而它的单测 `livelock_guard_has_two_stages` 是**绿的**——那条用例手搓了 `activations: 2..4` 的台账行，
而那是生产路径**产生不出来**的状态。

> **夹具直接构造中间状态，等于把「怎么到达这个状态」排除在检查之外**，而 bug 往往就在那一段。

同一批代码的 14 处变异点也全红过。**变异检查只能验「这行代码有没有用例盯着」，
验不了「这条链在真实状态下能不能走通」**——两者是不同的问题，别拿一个当另一个的保证。

### 检查项

- [ ] **带状态机的模块，至少一条用例走完整往返**：从初始状态出发，逐步调用真实的转换函数，
      断言每一步的状态与计数。一次都不碰「直接把对象摆成某个中间态」的夹具。
      > 实例：`livelock_guard_is_reachable_through_real_round_trips` 逐轮调 `activate_dormant` 五次，
      > 断言计数 1→2→3→4→5 并在 3 / 5 处踩到两道门。
- [ ] **夹具里出现 `status: "xxx"` / `state: Settled` / `count: 4` 这类直接摆位时，问一句**：
      生产路径怎么到这个状态？那一段有人测吗？
- [ ] **一个夹具服务两条路径时，确认两条要的前置条件不冲突**。
      > 实例：批 C 的遍历测试里，`promote` 只处理 `settled` 项、落账只处理 `skipped` 项，
      > 共用一个夹具必有一条落空——变异检查连抓两次，先是 promote、改完又轮到 persist。
- [ ] **用文本替换做变异检查时，先确认替换点唯一且正确**——否则变异本身会默默失效，
      而你把「用例没红」读成「用例不够强」或「代码是对的」。
      > 实例（2026-10-04）：验证 `from_ledger` 不变量时，`perl -0777 -pe 's|...|...|'（无 `/g`）
      > 只改了**第一处**，而同一行文本在 `queue.rs` 里出现两次（306 / 339）——被测的那个
      > 函数在 339。变异打在了别的函数上，用例自然绿着，差点当成「已验证」收了。
      > 做法：替换前 `grep -c` 数一下，或按行号改；**替换后把改动行打出来看一眼**。
      > 变异检查本身也会假绿。

- [ ] **测「只做一次」这类防重复逻辑时，确认夹具真的会触发第二次**。
      > 实例：两条复核同时回来会被 `while let … now_or_never()` 一次取光，循环只迭代一次，
      > 防重复标记就没有可观测效果；要让它们**错开**回来才测得到。

### 不变式用遍历写，不用逐条断言

同一条不变式散在 N 个地方时，写成**遍历**而不是 N 条独立断言：
逐条断言的毛病是**第 N+1 条加进来时没人会想起补一条**。

> 实例：`every_ledger_path_is_disabled_by_no_dismissed` 把五条台账路径列成数组逐一跑，
> 判据是零副作用（返回值都空、库文件逐字节不变、连 warning 都不许有），
> 末尾还有一条 `assert_eq!(names.len(), 5, "新加台账路径时这里也要加")`。

## 改状态机时：文档和实现一起改

改了状态集合或转换规则，**同一批里**回写：

- [ ] 枚举 / 常量的注释（说清每个状态谁写、何时写）
- [ ] 任务 PRD 与里程碑文档里引用这些状态的地方
- [ ] 依赖该状态的**其他**判据（收敛口径、过滤条件、观测计数）

> 实例：批 C 把三态改两态时漏了 PRD，而 PRD 自己的三处定义（收敛口径、激活判据、活锁门）
> 都建立在旧模型上——文档与实现相互矛盾，且矛盾的那一侧正是已被证伪的那个设计。
> dogfood 把它当 high 报了出来。
