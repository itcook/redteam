## Recommendation

> 先修正裁决，再完成审核制品；当前证据不足以报告“三个 Important 阻塞项”。
>
> 1. **Q1、Q2 是成立的测试缺口，基础等级应为 🔵。** Q1 的 Reference 分支确实没有非零样本，补一个真实声明及跨组单次引用即可锁住分类行为。Q2 应以本次改动的 `src/cli/mod.rs:677` 格式串为主锚，`tests/review_e2e.rs:531` 作为辅助证据；不要让未修改的测试文件成为唯一定位，否则违反自己的 InScopeFiles 过滤。
>
> 2. **重新计算 precedent weighting。** Skill 要数“至少两个独立相关先例提交，各自发生过后续修复”，不是“一个先例有两个以上修复提交”。还须核实这些先例与具体问题的关联，不能把同一个大文件的历史修复数量直接套给所有发现。在这一步证据齐全前，撤销三条统一升级为 🟡 的结论。
>
> 3. **Q3 的反向兼容问题真实，但当前应归 💭 兼容边界。** 用户明确批准删除 `weak_cut`，当前契约保证的是新程序读旧报告，没有保证旧程序读新报告。补充说明即可，不能据此要求恢复已批准删除的字段。另一个细节要说准确：revert 恢复代码，**不会恢复已写入报告的字段**，所以“单 commit revert 即恢复”不能证明持久化格式可无损回退。
>
> 4. **补查真正影响受支持方向的 Q4：旧报告经新程序恢复时，未知分种被写成零。** 已有测试本身给出了输入：旧 JSON cross_edges=4、无三个分种字段 → 新 Deserialize 三键全 0 → run_resume clone 再写新报告。这会使新输出违反“总数等于分种之和”，并把“历史未采集”呈现成“实测为零”。做一个最小的 deserialize→serialize 复现，再交窄范围 claim verification；若确认没有有效性标记，这是比 Q3 更直接的 🟡 观测数据正确性问题。建议方向是保留“未采集”状态，而不是从总数猜分种。（注：窄验证后传播面收窄为仅 resume 通道，按 Weakened 降 🔵。）
>
> 5. **纠正 `cross_import=0` 的结论强度。** 当前算法保证 Import 强边不跨组，所以 PR181 的零值验证了分组不变量，不能证明语义分组没有增量价值；无 import 关系的语义关联正是该计数无法观测的部分。本提交改动的 plan、followup、PRD 和代码注释仍在审核范围内，不应整体排除。相关说明最多作为 🔵 文档解释问题，别扩大到重设计 R8。
